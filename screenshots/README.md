# Screenshots for the Play Store listing

How to get real, reproducible screenshots of the mobile client against **neutral demo data** —
never against a real customer's projects, and never against the shared local dev database that
`npm run dev` in the server repo boots by default.

## Why a dedicated instance

The server repo's own `npm run dev` seeds (`seeds/agentiz.seed.ts`, `seeds/agentiz-projects.seed.ts`)
create projects named after this codebase's own work (`Биллинг`, `Инфраструктура`, `Demo Repo`…).
That is fine for local development, but wrong for a screenshot that ends up on Google Play: it
would show internal-sounding project names to the public, and it would be reused every time
someone reads a name meant for developers, not users. Screenshots need their **own** database, with
**their own** neutral content, generated by **one seed** so the recipe below is repeatable the next
time the listing needs refreshing.

That seed is `seeds/mobile-screenshots.seed.ts` in the server repo — off by default, on only for a
throwaway instance. It creates three small, invented, open-source-flavoured projects (see
[Mock data](#mock-data) below) and their tasks, using the `stub` executor and `finalAction: none`
pipelines from `AGENTS.md`'s own pattern (`seeds/agentiz-projects.seed.ts`): a task can go from
`new` to `succeeded` on a bare checkout, through the **in-process worker**, with no model
credentials and no repository token. One task is wired to fail on purpose (see the file's header
comment) so the failure screen is real too, not simulated.

## Recipe

Run this from the **server** repo root (`/prj/agentiz`, not `mobile-client`), so the mobile client
can be pointed at it as an ordinary server:

```bash
# 1. Fresh sqlite file + its own port — never the shared dev database on :17280.
rm -f .tmp/mobile-screenshots.sqlite
PORT=17281 DB_STORAGE=./.tmp/mobile-screenshots.sqlite AGENTIZ_WORKER_API_ENABLED=false \
  npx tsx --tsconfig ./tsconfig.runtime.json ./index.ts

# 2. No administrator exists yet on a fresh database — create one at:
#      http://localhost:17281/dashboard/init_user
#    Use a generic login (this project used demo / ScreenshotsDemo123! — it is thrown away with
#    the sqlite file, never reused for anything real).

# 3. Restart with the seed turned on — it defers until an admin exists (same rule as
#    agentiz-projects.seed.ts), so the first boot above never ran it.
PORT=17281 DB_STORAGE=./.tmp/mobile-screenshots.sqlite AGENTIZ_WORKER_API_ENABLED=false \
  AGENTIZ_SEED_MOBILE_SCREENSHOTS=1 \
  npx tsx --tsconfig ./tsconfig.runtime.json ./index.ts
```

`AGENTIZ_WORKER_API_ENABLED=false` is what turns on the **in-process local worker** — the seeded
projects need one to turn a task into a real run.

### The seed does not clean up an existing database

Every non-production boot also runs the server's own default seeds
(`agentiz.seed`, `agentiz-projects.seed`) — that is `seeds/index.ts`, shared with the rest of the
server, not something `mobile-screenshots.seed.ts` controls. On a **fresh** sqlite file (step 1)
those create their own small set of projects alongside the three neutral ones. Delete the extra
ones once, through the panel's generic CRUD (`/dashboard/model/AgentProject`, the row's **⋮ → Delete**)
before taking screenshots — a fresh file needs this exactly once, right after the first boot in
step 3.

### Running the seeded tasks for real

The seed creates tasks but does not run them — that has to happen through the ordinary "Запустить"
button on each task (`http://localhost:17281/dashboard/agentiz/projects/<slug>/tasks`), the same
action a person would take. Run enough of them to get a spread of states before screenshotting the
**mobile** client:

- most tasks: a plain run, so it lands on `succeeded` in a few seconds (the stub executor does no
  real work — the whole pipeline finishes near-instantly);
- the task tagged `ci-flake` (in *Weather Now*) is wired to a role with an unregistered executor
  kind (`config: { executor: 'offline-only' }`) — running it produces a genuine `failed` run, not a
  faked one, because `resolveAgentExecutor` really throws for an unknown kind;
- leave **one or two tasks per project un-run** — a task that has never had a run is its own state
  (`Новая`) and belongs in a screenshot as much as a finished one;
- the task carrying a seeded human comment (*Recipe Box* → «Переключатель метрических/имперских
  единиц…») is best left un-run too, so its screenshot is a discussion thread, not a run report.

### Pointing the mobile client at it

Build the **wasm** target (the shared UI, no Android emulator needed — see the main
[`README.md`](../README.md#web-wasm--the-quickest-way-to-see-it)):

```bash
cd mobile-client
./gradlew :composeApp:wasmJsBrowserDevelopmentRun
```

Open the app (`http://localhost:8081/` by default) and type `http://localhost:17281` into the
**Сервер** field on the login screen — the field takes any reachable origin, there is nothing to
rebuild. Sign in with the login created in step 2.

#### First run inside the full agentiz checkout: a Yarn/Corepack error

`kotlinWasmNpmInstall` can fail immediately with *"This project's package.json defines
`packageManager: yarn@4.14.1`. However the current global version of Yarn is 1.22.22."* This has
nothing to do with the mobile client's own dependencies: Gradle's downloaded classic Yarn, before
doing anything else, walks up from its working directory through **every** ancestor `package.json`
looking for the first one that declares a `packageManager` field, and refuses to run at all unless
that value looks like a classic Yarn (`yarn@0.` or `yarn@1.`). Because this repo is checked out as a
git submodule *inside* the agentiz server checkout, the first ancestor with such a field used to be
the **server's** `package.json` (`yarn@4.14.1`, Corepack/Yarn Berry — correct for that Node project,
irrelevant to this one). `mobile-client/package.json` (committed) is what the walk finds first
instead now, with a version classic Yarn accepts — so this only ever bites a clone that predates
that file, or a checkout laid out differently. `SKIP_YARN_COREPACK_CHECK=1` in the environment
disables the same check outright, if it ever resurfaces.

### Phone-shaped screenshots from a browser

The wasm build renders the exact same UI a phone shows — same commonMain, per the main README's
"Only the entrypoint and the default server URL are per-platform" — so a browser window resized to
a phone's CSS pixel size **is** a phone screenshot, with no device frame needed for Play's own
listing requirements (min 320px, max 3840px, aspect ratio no more than 2:1). This project's own
screenshots were taken at **412×915** (a common mid-range Android viewport) using Playwright,
resizing the browser before every capture and letting the layout reflow — Compose Multiplatform
has no separate "mobile breakpoint" to fight the way a responsive website would.

A headless browser needs software WebGL or the canvas never paints (see the main README's
[WebGL note](../README.md#the-browser-needs-webgl)) — pass
`--use-gl=angle --use-angle=swiftshader` to whatever launches the browser, or use a Playwright MCP
tool that already runs headless Chromium (this project's screenshots were taken that way, and
needed no extra flag — Playwright's bundled Chromium already renders the canvas headless).

### Driving the UI: it is one `<canvas>`, not a form

Compose for Web renders everything onto a single `<canvas>` (found inside a shadow root — plain
`document.querySelector('canvas')` returns nothing, it has to walk shadow roots) and mirrors an
accessibility tree in hidden, zero-size DOM nodes underneath it, purely for screen readers. Two
things follow, both learned by trial and error taking this project's own screenshots:

- **Do not click the accessibility node.** Playwright's ordinary locator-based click resolves the
  hidden `<div role="textbox">` correctly, then refuses because the real, visible `<canvas>` sits on
  top intercepting pointer events — which is exactly correct, and exactly not where a real user's
  click would land either.
- **Synthetic DOM events do not reach Compose's input handling.** A JS-side
  `canvas.dispatchEvent(new PointerEvent(...))` changes nothing — Compose's own event handling does
  not react to it. What works is a **trusted** click at real viewport coordinates, i.e. Playwright's
  own `page.mouse.click(x, y)` (CDP-level input, indistinguishable from a real user) — read the
  coordinates off `browser_snapshot({ boxes: true })`'s `[box=x,y,w,h]` for the field or button in
  question, click its centre, then drive text entry with `page.keyboard.type(...)`. A Playwright MCP
  tool that only takes an element ref or CSS selector (`browser_click`) cannot do this; one that runs
  arbitrary Playwright code against `page` (this project used `browser_run_code_unsafe`) can.

## Mock data

Three small, invented, neutral demo projects and their tasks, defined in
`seeds/mobile-screenshots.seed.ts` — no client names, no real repositories, nothing that has to stay
private. Themes were picked the way most developer-tool demos pick theirs: small, recognisable,
open-source-flavoured apps everyone has an intuition for, so a screenshot reads as "a real small
project" rather than "a placeholder."

| Project | What it is | Sample task |
| --- | --- | --- |
| **Weather Now** | A small open-source weather app | «Температура показывается в °F для пользователей из Великобритании» |
| **Recipe Box** | A recipe catalogue with tags and a shopping list | «Поиск показывает рецепт дважды при фильтре по тегу» |
| **Trailhead** | A hiking-trail tracker: GPS recording, offline maps | «Экспорт в GPX даёт битый файл для маршрутов с паузами» |

Extending or refreshing this set (a new screen needs a state the current data does not have) means
editing that one seed file — never hand-editing rows in a screenshot database, which is exactly
what would make the next refresh unreproducible.

## What is actually committed here

`play-store/` holds the curated, final PNGs used for the Play Store listing and this README — a
small, hand-picked set, not every screen this recipe can produce. Regenerating them means repeating
the recipe above and re-exporting only the ones that changed; there is no build step that produces
these files automatically.
